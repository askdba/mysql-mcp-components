# Changelog

## [Unreleased]

- Moved from askdba/myvector with history: `component_mcp_guard`, `component_mcp`, the `mysql_mcp` SQL tool pack, the `mysql-mcp` image, and their tests.
- Own build (`CMakeLists.txt`, `scripts/build-components-docker.sh`), CI and image publishing.

Changes made in askdba/myvector before the move, not yet released there (moved from its changelog):

### Security
- **`component_mcp` no longer reports a completed statement as timed out** (review on askdba/myvector#308, [#256](https://github.com/askdba/myvector/issues/256)). A statement that returned without an error was turned into error 1317 when the call-time-limit watchdog's `KILL QUERY` had succeeded, so that a killed `SELECT SLEEP(…)` would not look successful. But `KILL QUERY` also succeeds on an idle session. A statement that completed just before the KILL, possibly a write, was then reported as failed, inviting a retry that repeated it. Results are no longer converted: a statement stopped with an error still fails with 1317, and a killed `SLEEP()` returns 1. `scripts/test-mcp-endpoint.sh` checks both at a 3-second limit.
- **`component_mcp_guard` fails closed without `component_reference_cache`.** The server delivers event tracking to components through `component_reference_cache`, set up at startup. Without it (an install that lacks the file, as a server build of only `mysqld` did in the RFC 0001 §10 fuzzing setup), the guard loaded and registered its settings but saw no statements, so `MCP_USER` sessions, the endpoint's included, ran unrestricted. Now:
  - **At install:** the guard requires the cache's `reference_caching_channel` service, so if the cache is not loaded, `INSTALL COMPONENT` fails with error 3534, and `component_mcp`, which requires the guard, cannot be installed either.
  - **A cache installed after startup** satisfies that requirement but does not repair event tracking: the guard installs and still sees nothing until the server restarts with the cache loaded. For that case, `component_mcp` checks before its first call as an `MCP_USER` account that the guard is counting statements, and refuses calls (error 1290) until it is.
  - **Plain logins** of `MCP_USER` accounts are then governed by their grants alone (documented in `docs/MCP_COMPONENTS.md`).
  - Verified on MySQL 8.4.11, 9.7.2 and 26.10.0, with the cache removed (3534), and with it installed late (1290).
- **`component_mcp` stops tool calls that run too long** (found by the RFC 0001 §10 fuzzing run, [#256](https://github.com/askdba/myvector/issues/256)). Calls run on the endpoint's I/O threads. A statement that never ended (the fuzzer's `SELECT SLEEP(184467440737095516160.2)`) held its thread for good, connections assigned to that thread queued up to Router's limit of 64, and then the endpoint refused every connection until a restart. Any token holder could do this. The new `mcp_http.query_timeout_seconds` (read-only, default 30, as mysql-mcp-server's `MYSQL_QUERY_TIMEOUT_SECONDS`) sets when a call's statement is cancelled: past it, a watchdog runs `KILL QUERY` from a session of the same account (repeated every 5 s while the call runs), and the call fails with error 1317. It is a cancellation, not a hard bound: a statement that completes after the deadline but before a KILL reaches it returns its result. `scripts/test-mcp-endpoint.sh` checks the default, that `SELECT SLEEP(20)` and `DO SLEEP(20)` stop at a 3-second limit, and that the next call works.
- **`component_mcp` no longer lets a long error message abort `mysqld`** (found by the RFC 0001 §10 fuzzing run, [#256](https://github.com/askdba/myvector/issues/256)). MySQL 26.10.0's command-service backend (`csi_advanced_command`) `strcpy()`s a failed statement's error message into a 256-byte stack buffer, while server messages run to 512 bytes. Any token holder could send `SELECT 1 LIMIT <250-character name>` (error 1327, "Undeclared variable: …") and kill the server: glibc's fortify check printed "buffer overflow detected" and aborted (signal 6). The endpoint now provides its own consumer error service, which delegates to the server's but hands that copy at most 255 bytes, cut at a character boundary. The full message still reaches the reply. `scripts/test-mcp-endpoint.sh` checks the 300-byte message and that the server stays up (before this change the check killed `mysqld`). The server bug itself is being reported upstream.
- **`component_mcp`: one account can no longer evict other accounts' sessions** (found by the security review for RFC 0001 §10, [#256](https://github.com/askdba/myvector/issues/256)). The `Mcp-Session-Id` table (4096 entries) dropped its least recently used session when full. Repeated `initialize` calls from one token could therefore end every other account's sessions (their next request got 404). Each account now keeps at most 64 sessions, a new one replacing that account's own least recently used. When the table is full of other accounts' live sessions, `initialize` gets 503. `scripts/test-mcp-endpoint.sh` checks 70 sessions of one account against another account's session.
- **`component_mcp`: token hashes stay out of logged SQL** (found by the security review for RFC 0001 §10, [#256](https://github.com/askdba/myvector/issues/256)). The token-table lookup put the presented token's hash in its statement text, so it reached the general log (when enabled), the processlist and performance_schema statement history, whose readers need not have access to `mysql.mcp_tokens`. A hash there allows an offline guess of a weak token. The lookup now runs fixed text over the unexpired rows and compares the hash in the endpoint in constant time. Requests share a snapshot of the rows, read again once it is a second old: unknown tokens cost at most one table read per second, and issuing or revoking a token takes effect within a second (it was the next request). `scripts/test-mcp-endpoint.sh` checks the general log for the hashes of a valid and an unknown token (both appeared before), and that 50 unknown tokens read the table at most once a second.
- **`component_mcp`: a token runs only as its exact account** (found by the security review for RFC 0001 §10, [#256](https://github.com/askdba/myvector/issues/256)). Impersonated sessions are matched against the grant tables like a login. So a token mapped to an account that does not exist, such as a dropped `app@localhost`, ran as a wider existing entry such as `app@'%'`, with that account's grants. If that account lacked `MCP_USER`, the guard did not restrict it either; reproduced on 26.10.0 by reading `mysql.user`. The endpoint now checks the session's `priv_user` and `priv_host` against the mapped account and refuses a mismatch with error 1045, for tool calls and for the token-table reader. `scripts/test-mcp-endpoint.sh` checks both cases.
- **`component_mcp`: deeply nested JSON no longer crashes `mysqld`** (found by the security review for RFC 0001 §10, [#256](https://github.com/askdba/myvector/issues/256)). rapidjson parses recursively, so a request whose body nested half a million arrays overflowed the I/O thread's stack (SIGSEGV). Only a token holder could send one, since the body is parsed after authentication. The endpoint now refuses bodies nested more than 64 levels deep with JSON-RPC -32700, before parsing. `scripts/test-mcp-endpoint.sh` checks the refusal, the server staying up, the limit, and that brackets inside strings don't count.

### Fixed
- **`component_mcp_guard` is built with hidden symbol visibility.** It exported its service placeholders (`mysql_service_<name>`) with default visibility, and `mysqld` exports globals of the same names (`mysql_runtime_error`, `mysql_current_thread_reader`). In a `dlopen()`ed library the executable's definition wins, so the guard's placeholder could resolve to `mysqld`'s own, and installing or uninstalling the guard could overwrite it. Found by AddressSanitizer as an ODR violation while building the RFC 0001 §10 fuzzing run. Only `list_components` stays exported. The MyVector component has the same overlap (and `mysql_udf_metadata`), but its UDFs are loaded by symbol name, so it needs a narrower fix, tracked separately.

### Changed
- **`component_mcp_guard` no longer subscribes to command events on 9.0+** ([#256](https://github.com/askdba/myvector/issues/256), RFC 0001 §10 guard overhead). They were used only to notice `COM_RESET_CONNECTION` in MCP sessions, but every client's commands paid for the dispatch: about 1% of the instructions of a point select. On 9.0 and later the guard reads the MCP session's `max_execution_time` at each of its statements instead (`mysql_system_variable_reader`) and restores the limit when it is 0 or above it; 8.4, which has no such reader, keeps command events. `scripts/test-mcp-guard.sh` now resets an MCP session with `COM_RESET_CONNECTION` (Python connector) and checks that the limit comes back, on 8.4, 9.7 and 26.10.

The `MCP-Protocol-Version`, `Mcp-Method` and `Mcp-Name` headers are checked against the body, and invalid requests get 400 with the revision's JSON-RPC errors (-32020 header mismatch, -32602, -32600). An `MCP-Protocol-Version` header naming a version not served now gets JSON-RPC -32022 with the supported versions instead of a plain-text 400, in either era. Results carry `resultType`, `serverInfo` in `_meta`, and cache hints on `server/discover` and `tools/list`. `scripts/test-mcp-endpoint.sh` checks each rule (28 new checks); `scripts/test-mcp-conformance.sh` runs MCP Inspector (`--protocol-era modern`) and the Python SDK in 2026-07-28 as well as the session era (41 checks).

Results and their limits are in `docs/MCP_COMPONENTS.md` (Overhead on non-MCP traffic): the guard costs about 2.3% of a point select's instructions (with askdba/myvector#276), mostly MySQL's event dispatch; p99 is within noise on a shared host.

- **`component_mcp` Streamable HTTP sessions and version negotiation** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). Protocol versions 2025-11-25, 2025-06-18, 2025-03-26 and 2024-11-05 are negotiated (unsupported: the newest), and an unsupported `MCP-Protocol-Version` header gets 400. `initialize` issues an `Mcp-Session-Id` bound to the token's account; unknown or expired ids get 404, another account's 403, and `DELETE` ends a session. Idle expiry is `mcp_http.session_timeout_minutes` (new, default 30). `POST` requires a JSON `Content-Type` and an `Accept` listing JSON and SSE, as the Go SDK; `GET` gets 405. The stateless 2026-07-28 revision is a follow-up ([#273](https://github.com/askdba/myvector/issues/273)).

A call whose token maps to an account with `SUPER`, `SYSTEM_USER` or `MCP_ADMIN` fails with error 1227 before any statement runs, for the single token and table tokens alike, checked on every call. Before, such a token ran unrestricted (the guard only restricts `MCP_USER` accounts). `scripts/test-mcp-endpoint.sh` checks root, a `SYSTEM_USER` and an `MCP_ADMIN` account.
- **`component_mcp` token table** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). `src/mcp/endpoint/mcp_tokens.sql` creates `mysql.mcp_tokens` (token SHA-256 to `user@host`, optional expiry) and the locked reader `'mysql.mcp'@'localhost'` (SELECT on that table only). The endpoint maps a bearer token to its account through `mcp_http.token_sha256` first, then the table, so any number of tokens and accounts can be issued and revoked with `INSERT` / `DELETE`. `scripts/test-mcp-endpoint.sh` checks two accounts, expiry, revocation, that MCP sessions cannot read the table and that nobody can log in as the reader.
- **`component_mcp` TLS and bind address** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). `mcp_http.bind_address` (default `127.0.0.1`), `mcp_http.ssl_cert` and `mcp_http.ssl_key` (all read-only). With both files set the endpoint serves HTTPS; plain HTTP is allowed only on loopback, so a non-loopback address without TLS fails the install (RFC §5.3). `scripts/test-mcp-endpoint.sh` checks both refusals, HTTPS on loopback and from another container, and plain HTTP to the TLS port.
- **`component_mcp` core tools** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). Besides `list_databases` and `run_query`: `list_tables` and `describe_table` (tool pack, arguments passed as hex literals), `ping` and `server_info`, with mysql-mcp-server's names and arguments; the catalog and status tools carry the MCP `readOnlyHint` annotation. `scripts/test-mcp-endpoint.sh` checks each, argument errors, and that quotes and backslashes in arguments stay literal.
- **`component_mcp` status variables for the bounded consumer.** `mcp_http.last_rows_retained`, `mcp_http.last_bytes_retained` and `mcp_http.last_rows_stored` (the row count the default consumer handed over, observed independently) report what the consumer kept for the last statement an endpoint call ran (rows, and bytes charged for them). `scripts/test-mcp-endpoint.sh` now checks the bounds with them (4 rows for 1 MB values, 1001 for `LIMIT 1000000`, 65 for 8000 NULL columns), replacing peak-RSS checks that were noisy on CI ([#267](https://github.com/askdba/myvector/issues/267)).
- **`component_mcp` column masking** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). `mcp_http.mask_columns` (new, read-only) applies mysql-mcp-server's `MYSQL_MCP_MASK_COLUMNS` rules: values of result columns whose names contain a pattern (Unicode case-insensitive, patterns trimmed of Unicode whitespace) become `********`, NULL stays NULL. This closes the RFC's masking parity gap, so the endpoint does not need to disable `run_query` when masking is configured. `scripts/test-mcp-endpoint.sh` checks masked, unmasked, NULL and binary values.
- **`component_mcp` validates `Origin`** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). Against DNS rebinding, a request with an `Origin` header that `mcp_http.allowed_origins` (new, read-only, default none) does not list gets 403; requests without `Origin` are not affected. For a listed origin it handles CORS (preflight answered, replies carry `Access-Control-Allow-Origin`), so browser clients such as MCP Inspector connect directly. `scripts/test-mcp-endpoint.sh` checks refusal, allowed origins, case and prefix matching, and the CORS preflight and headers.
- **`component_mcp` serves calls concurrently, with session limits** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). `mcp_http.threads` (default 4) I/O workers each serve one call at a time; the spike had one. `mcp_http.max_sessions_per_account` (default 4) caps an account's concurrent endpoint sessions (error 1203), since `max_user_connections` does not apply to them, and the sessions are now subject to `max_connections` (error 1040) instead of bypassing it. `scripts/test-mcp-endpoint.sh` checks overlap of 4 calls, the cap and `max_connections`.
- **`component_mcp` refuses locked accounts** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). Impersonated sessions skip the login checks, so the endpoint reads `account_locked` from the session's security context and fails the call with error 3118 before any statement runs. `scripts/test-mcp-endpoint.sh` checks lock, both tools and unlock.
- **`component_mcp` bounded row consumer** (RFC 0001 Phase 5, [#256](https://github.com/askdba/myvector/issues/256)). `run_query` sessions use the component's own row and value consumer services, which stop retaining rows past 1001 rows or 4 MiB of values while a statement runs, so a large explicit `LIMIT` or wide rows no longer buffer the whole result in `mysqld`. The budget counts values plus the per-row and per-cell overhead of the default consumer, NULL cells included. `scripts/test-mcp-endpoint.sh` now has 41 checks, including peak RSS for `LIMIT 1000000` and for 1 MB rows, 8000 NULL columns, DOUBLE widths, and errors raised after some rows.
- **`component_mcp` (RFC 0001 Phase 4 spike, MySQL 26.10).** An MCP Streamable HTTP endpoint inside `mysqld` on MySQL Router's HTTP server (the libraries `component_mysql_rest_service` links), built in the server tree with `MYVECTOR_BUILD_MCP_ENDPOINT=ON ./scripts/build-component-26.10-docker.sh`. It is not for production.
  - **Endpoint:** loopback, plain HTTP, one bearer token (`mcp_http.token_sha256`) mapped to one account (`mcp_http.account`).
  - **Tools:** `list_databases` (tool pack) and `run_query` (one statement).
  - **Sessions:** each call runs in an impersonated `"local"` session, announced with a connection audit event so that `component_mcp_guard` enforces its policy there.
  - **Phase 4 exit criterion met:** through the endpoint, an `MCP_USER` account's write and `mysql` read are refused, and an account without `MCP_USER` is not restricted.
  - **Measured:** 95 s build, 3.1 MB, 3 threads (MRS: 265 s, 21 MB).
  - **Tests:** `scripts/test-mcp-endpoint.sh` (30 checks) and the `mcp-endpoint` CI job. `docs/MCP_COMPONENTS.md` has the details and the Phase 5 facts (locked accounts, `max_user_connections`, Basic-only Router auth).
- **`component_mcp_guard` tests for views, multi-statement packets and parity** (RFC 0001 §5.2 item 7, Q3). `scripts/test-mcp-guard.sh` now has 102 checks on 8.4.11, 9.7.2 and 26.10.0.
  - **Views:** a view over another schema or over `mysql` is refused, nested views included (the rules see base tables).
  - **Multi-statement packets:** a write or disallowed read in a later statement of one packet is refused, and nothing is written.
  - **Parity table:** `sql/mcp/guard-parity.tsv` (34 statements) has the shared verdicts of mysql-mcp-server's `run_query` validator and the guard, with the reason for each difference. The guard column is checked here; mysql-mcp-server checks the other.
  - **Known limitation, documented:** reads inside stored functions and triggers aren't seen by the schema rules, because the server raises no table access events for tables the calling statement locked. Writes inside them are still refused. `docs/MCP_COMPONENTS.md` (Limits) gives the mitigation (grants), and a test check shows the behavior ([#247](https://github.com/askdba/myvector/issues/247)).
- **`mysql-mcp` Docker images** (Phase 3 of RFC 0001). `ghcr.io/askdba/mysql-mcp:<8.4|9.7|26.10>` (also tagged with the exact release) is the official MySQL image of the release the component is built for, with `component_mcp_guard` and the `mysql_mcp` tool pack installed on first start. `MYSQL_MCP_USER`/`MYSQL_MCP_PASSWORD` create an MCP account (`MCP_USER`, tool pack, read access to `MYSQL_MCP_DATABASES`), and `MYSQL_MCP_ALLOWED_SCHEMAS`/`MYSQL_MCP_MAX_EXECUTION_TIME_MS` persist guard settings. - **`component_mcp_guard` enforcement** (Phase 2 of [RFC 0001](https://github.com/askdba/mysql-mcp-server/blob/main/docs/rfc/0001-mysql-component-architecture.md)).
  - **MCP sessions:** sessions of accounts holding `MCP_USER` (and not `MCP_ADMIN`) are checked against `mcp.*` settings inside `mysqld`. The checks run on the server's query, table-access and connection events.
  - **`mcp.read_only` (default ON):** only reads, even with write grants. It uses an allowlist of `sql_command` classes and also refuses `SELECT … INTO OUTFILE`, locking reads, `SET GLOBAL` and `CALL` outside `mysql_mcp`.

  - **`mcp.enabled`:** a kill switch.
  - **Errors and administration:** denials fail with error 1290. Changing `mcp.*` needs `MCP_ADMIN`.
  - **Status variables:** `mcp.sessions_connected`, `mcp.statements_total`, `mcp.statements_denied` and `mcp.table_access_denied`.
  - **Tests:** `scripts/test-mcp-guard.sh` grew from a lifecycle test to 65 checks (enforcement, administration, persistence, restart, uninstall, `lower_case_table_names=1`), passing on MySQL 8.4.11, 9.7.2 and 26.10.0. `src/mcp/guard/test_mcp_guard_policy.cc` unit-tests the classification.

It is opt-in and does not change the MyVector build: `MYVECTOR_BUILD_MCP=ON ./scripts/build-component-<ver>-docker.sh` also builds and packages `component_mcp_guard.so`. `scripts/test-mcp-guard.sh <ver> <artifact-dir>` checks install, privilege registration, grants, restart and uninstall against the official `mysql:<ver>` image. - **`mysql_mcp` SQL tool pack 1.0.0** (`sql/mcp/mysql_mcp.sql`, Phase 1 of RFC 0001). One `SQL SECURITY INVOKER` procedure per catalog tool of mysql-mcp-server (18 tools), each returning exactly the result set of the Go server's own query. Each runs fixed statement text as a prepared statement with bound arguments, so names compare exactly as they do for the Go server on MySQL 8.0 through 26.10 and MariaDB 11.4 and 12.3. ### Fixed
- **`component_mcp_guard`: sessions opened by components were never guarded** (RFC 0001 Phase 4, open question 4). A component's `"local"` command-service session that impersonates an MCP account raises no connection event, so the guard never marked it as an MCP session. On 9.7.2 such a session could write, read `mysql.user` and run without the time limit.
  - The guard now classifies an unclassified session from its privileges at its first statement. A "not MCP" marker keeps the cost at one grant check per session.
  - `mcp.sessions_connected` is decremented when the session's THD ends, which also covers sessions without a disconnect event.
  - These sessions also start **unaudited** (no events at all), so a component must emit connection audit events for them. This is documented in `docs/MCP_COMPONENTS.md`, and `component_mcp` will do it.
  - `scripts/test-mcp-guard.sh`: 123 checks on 8.4.11, 9.7.2 and 26.10.0, with the test-only `component_mcp_session_probe`. The unfixed guard fails the local-session checks.
- **`component_mcp_guard`: table reads the schema rules could not see** (found reviewing the code behind askdba/myvector#247). The server raises table access events only for `SELECT`, data changes, `ANALYZE` and `HANDLER READ`. An MCP session could therefore read any table, `mysql.user` included, past `mcp.allowed_schemas` and `mcp.deny_system_schemas`:
  - directly, with a subquery in `SET` or `DO` (`SET @x = (SELECT … FROM mysql.user); SELECT @x`), also through `PREPARE`/`EXECUTE`;
  - as a yes/no oracle, with a subquery in `SHOW … WHERE` or in a `CALL` argument;
  - checksums only, with `CHECKSUM TABLE` / `CHECK TABLE`.
